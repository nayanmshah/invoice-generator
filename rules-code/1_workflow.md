# Code Workflow

**Code = code implementation phase.** Implements features from development plan (greenfield, extend, add-feature) or applies fix (from debug handoff or diagnose+fix in one flow for brownfield-fix-bug).

0. **Expertise check (on every message):** Before responding to ANY message — including follow-ups and subsequent turns — check if the user or Nayan asks something outside this mode's expertise (per MODE RESTRICTION). If yes, hand off per `.nayan/guidance/expertise-handoff.md`. Do not attempt in-place or create a subtask. Do not skip on the next message. Example: user asks "Create PRD" → hand off to prd with skillHint=prd-creation.

1. **Verify prerequisites** — **Always check first** (whether entered via workflow or directly). **Pipeline-aware:** **Sprint-based** (greenfield, brownfield-extend, brownfield-add-feature, brownfield-migrate): development-plan.md, architecture.md — if missing, redirect to **plan** per sdlc_prerequisites rule. **Brownfield-fix-bug:** Bug report (or diagnosis + fix instructions from debug handoff) and codebase — if missing, ask user; do NOT redirect to plan (no development-plan). **Brownfield-refactor:** refactor-scope.md and codebase (from QA handoff) — if missing, redirect to **qa**; do NOT redirect to plan. When entered directly with missing prereqs: use new_task to redirect per sdlc-prerequisites.
2. **REPO_STRATEGY:** Use from handoff (USER_INPUTS) when present. For fix-bug or refactor (no Plan handoff), **detect from codebase**: one `.git` at root → single; `frontend/.git` and `backend/.git` present → multi. Pass REPO_STRATEGY to QA in handoff. See `.nayan/guidance/decoupled-fullstack-repo-strategies.md`.
3. Read inputs per pipeline. **Sprint-based:** development-plan.md and architecture.md. **Brownfield-fix-bug:** Diagnosis and fix instructions (from debug handoff) or bug report; use systematic-debugging skill when diagnosing in-code. **Brownfield-refactor:** refactor-scope.md from QA. **For large files:** Use search-first and targeted reading per `.nayan/guidance/file-reading-strategy.md` — search for relevant sections (sprint tasks, folder structure, tech stack, prototype paths) then read only needed ranges with offset/limit. **When UI tasks present:** Reference the approved UX prototype (paths in development-plan) as the authoritative source for UI design and look-and-feel; implement to match it **using the tech stack from architecture.md** (documented in architecture.md).
4. **Todo structure (pipeline-aware):** When creating or updating the todo list, use the structure per pipeline. **Sprint-based** (greenfield, extend, add-feature, migrate): Each feature sprint (S0, S1, S2...) as separate todos; final todo: "Hand off to QA (new_task)" (see handoff-schema.md); optional: "Deployment Sprint (handled by deploy mode after QA and Secure)". **Brownfield-fix-bug:** Todos: Diagnose, Apply fix, Hand off to QA. No sprints. Deploy is conditional — orchestrator asks after Secure. **Brownfield-refactor:** Todos: Apply refactor per refactor-scope, Hand off to QA. Deploy always (handled by deploy mode after QA and Secure). See sprint_protocol.md.
5. Implement sprint-by-sprint per sprint_protocol.md (announce, ask, implement, explain, wait, proceed)
6. **HITL:** After each task, ask user to verify locally before proceeding
7. When all sprints complete: commit, push, create PR (human merges); **strict handoff to QA** — do not skip QA or hand off to deploy. When there is a code change (greenfield or brownfield), Code must hand off to QA; QA then hands off to Secure. See `.nayan/guidance/code-quality-security-gates.md`.

See code-implementation skill and sprint_protocol.md for full methodology. See real_stack_enforcement.md for tech stack rules.
