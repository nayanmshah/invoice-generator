# PRD Workflow

PRD mode covers PRD creation and refinement in two phases.

## Before Any Work

0. **Expertise check (on every message):** Before responding to ANY message — including follow-ups and subsequent turns — check if the user or Nayan asks something outside this mode's expertise (per MODE RESTRICTION). If yes, hand off per `.nayan/guidance/expertise-handoff.md`. Do not attempt in-place or create a subtask. Do not skip on the next message. Example: user asks "Fix GitHub issue" → hand off to code with skillHint=issue-resolution-workflow.

## Phase 1: Initial PRD (from brainstorm or user idea)

1. **Read the user's product idea or draft.** If the user provides **minimal details** (e.g., one-line idea, vague concept), **do NOT proceed** to create initial PRD. **Switch to brainstorm mode** — hand off so the user can explore and flesh out the idea there. PRD resumes when brainstorm hands off with a structured concept. **Orchestrator should route to brainstorm first** when minimal details — see orchestrator workflow; PRD loading here is a fallback when prd is reached directly. **When entered from brainstorm handoff** (e.g. after JIRA/SOW): use the **structured concept or aligned requirements summary** from the handoff message as the primary input for creating initial-prd; do not re-fetch JIRA/SOW unless the message or user asks for additional context. See prd-creation skill: "Minimal Input: Switch to Brainstorm Mode."
2. **When the PRD needs more details to get clarity**, ask additional questions in PRD mode. **Ask one question at a time** — do NOT batch multiple questions. Wait for the user's answer before asking the next. Do not assume or fill with placeholders — clarify with the user. Cover Problem, KPIs, Success Criteria, Users, Scope, Use Cases (steps, acceptance criteria, edge cases), Entities, Integrations, Error Handling, NFRs, UI/UX, Constraints. See prd-creation skill: "Clarity Through Questions." **When covering UI/UX:** Ask whether the user wants to share screenshots or UI mockups (e.g., Figma link, sketches, wireframes) for the prototype phase.
3. **Domain knowledge:** Ask for key domain terms, glossary, or business terminology. If user provides a draft, extract terms; otherwise ask: "What key domain terms should we define? (e.g. Order, Shipment, SKU, Campaign)"
4. **Use MCP when configured:** Jira, Confluence, Google Drive, etc. — fetch existing product specs, requirements, design docs, and stakeholder context. **Context inputs:** Per `.nayan/guidance/context-input-handling.md` — when user provides SOW doc (link/file), fetch full content; when user provides Jira ID, fetch full issue (description, attachments, comments). Use as input for use cases and entities. This enriches the PRD with real-world constraints and terminology.
5. Deconstruct to identify all requested capabilities (explicit and implied)
6. Enrich using Holistic Feature Mandate (CRUD+L for every entity)
7. Map data entities and lifecycle operations (use domain terminology from step 3)
8. Perform complexity assessment
9. Identify functional ambiguities; formulate clarification questions — **ask user**; do not assume
10. Create initial PRD with all 15 mandatory sections per `.nayan/guidance/prd-template-v2.md` (including Domain Glossary in Section 15 Appendix). **Keep all Sign-Off roles as Pending** — do NOT fill any role as Approved. Sign-Off is filled only when user identifies their role (Phase 2, before handoff).
11. **Run PRD gap validation** per `.nayan/guidance/prd-gap-validation.md` — verify all 15 sections present, no gaps; fix any failures
12. Validate: each use case has complete Steps, Acceptance Criteria; entities documented in Section 8; glossary in Appendix
13. **HITL:** Present PRD to user; wait for approval before refining

## Phase 2: Refined PRD (MVP scoping)

1. **Verify prerequisites** — **Always check first** (whether entered via workflow or directly). initial-prd.md required. If not passed: redirect to PRD Phase 1 per sdlc_prerequisites rule. When entered directly: if missing, use new_task to redirect per sdlc-prerequisites.

**Handback from prototype:** When prototype indicates requirements need adjustment based on UX findings, prototype uses new_task with mode=prd and message describing the required changes. PRD updates PRD per the message and hands off per 4_handoff.xml (greenfield → architect; brownfield-add-feature → architect, then architect hands off to prototype or plan). 2. Read initial-prd.md. **For large files:** Use search-first and targeted reading per `.nayan/guidance/file-reading-strategy.md`. **When refined PRD needs more details to get clarity** (gaps, ambiguities, incomplete use cases), ask additional questions in PRD mode. **Ask one question at a time** — do NOT batch multiple questions. Do not assume — clarify with the user before refining. **When covering UI/UX:** Ask whether the user wants to share screenshots or UI mockups (e.g., Figma link, sketches, wireframes) for the prototype phase. 3. **Use MCP when configured:** Jira, Confluence, Google Drive, etc. — fetch updated specs, acceptance criteria, backlog items, or stakeholder feedback to refine MVP scope. **Context inputs:** Per `.nayan/guidance/context-input-handling.md` — fetch SOW or Jira context when user provides them. 4. Deconstruct to identify all capabilities 5. Enrich using Holistic Feature Mandate (CRUD+L) 6. Identify Critical Path Journey for MVP 7. Segregate: Core MVP vs Deferred (with rationale) 8. Validate: each use case has complete Steps and Acceptance Criteria; entities documented 9. Preserve all 15 sections per `.nayan/guidance/prd-template-v2.md` (including Domain Glossary in Section 15 Appendix); condense where needed 10. **HITL:** Present refined PRD to user; confirm "PRD has all information needed for architecture"; wait for user to approve content. **Do not mark Approved or hand off (new_task) or call attempt_completion until user has given explicit sign-off.** 11. **Plan readiness check (after content approval):** **MANDATORY: Ask creator** "Which role are you? (PM, Engineering Lead, or Design)" — do NOT assume or default to PM. Wait for user to identify their role, then record approval for that role only (Approver Name, Sign-Off Date). Other roles stay Pending. Verify (a) PRD Sign-Off (Section 1) has all three roles (PM, Engineering Lead, Design) Approved with Approver Name and Sign-Off Date filled for each — **block if Pending, Needs Revision, or missing Name/Date**; (b) refined-prd has Use Cases (7), Entities (8), Non-Functional Expectations (11), Domain Glossary (15 Appendix). See plan_input_requirements rule 12. **If other roles Pending:** "The remaining roles are still Pending. Share the PRD with the people in those roles for their approval." — per prd-sharing-sign-off. One user = one role; no single user may approve for multiple roles. 13. **Run PRD gap validation** per `.nayan/guidance/prd-gap-validation.md` — verify all 15 sections present, Sign-Off complete, plan-required sections sufficient; fix any failures before handoff 14. **Handoff** only when all three roles Approved. 15. **PRD sharing for sign-off:** When user needs to share PRD with another person (PM, Engineering Lead, Design) for approval: (a) **Manual hand-off:** Instruct user to share the task (Share button); direct recipient to open shared link and complete their role's Sign-Off in Section 1. Shared view should navigate recipient to PRD approval process. (b) **Slack/Gmail:** If configured, offer to send refined PRD via Slack or email. See `.nayan/guidance/prd-sharing-sign-off.md`

See prd-creation and prd-standards skills for full methodology. See sdlc_human_gates rule for PRD sign-off and plan input readiness. **Handoff:** Greenfield → architect. When pipeline is **brownfield-add-feature** (add/enhance feature with PRD first), hand off to **architect** (architect produces architecture impact per architecture-impact-add-feature.md, then hands off to prototype or plan). See 4_handoff.xml.

**MCP:** When MCP servers (Jira, Confluence, Google Drive, etc.) are configured, use them proactively to gather product specs, requirements, and stakeholder context for richer PRDs. **Context inputs:** Per `.nayan/guidance/context-input-handling.md` — fetch SOW or Jira context before creating or refining PRD.
