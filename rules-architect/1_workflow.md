# Architect Workflow

You produce **architecture.md** only. You do not create development-plan.md. When architecture is complete and user has approved, hand off to **prototype** (when UI) or **plan** (dev-plan phase, when API-only).

## Before Any Work

0. **Expertise check (on every message):** Before responding to ANY message — including follow-ups and subsequent turns — check if the user or Nayan asks something outside this mode's expertise (per MODE RESTRICTION). If yes, hand off per `.nayan/guidance/expertise-handoff.md`. Do not attempt in-place or create a subtask. Do not skip on the next message. Example: user asks "Implement this" → hand off to code with skillHint=code-implementation.

## Architecture (from prd, brainstorm, or brownfield entry)

1. **Determine context:** Greenfield (new product) → use `.nayan/guidance/architecture-greenfield-structure.md`. Brownfield A (extend existing) → use `.nayan/guidance/architecture-brownfield-structure.md`. **Brownfield Migrate (product migration legacy→new):** pipelineId=brownfield-migrate → use `.nayan/guidance/architecture-brownfield-structure.md`; input = migration brief or condensed scope, existing (legacy) architecture or system context, codebase; document pre/post architecture, migration strategy, data migration, cutover per `.nayan/guidance/brownfield-migration-use-cases.md`; then hand off to prototype (when UI) or plan. **Brownfield B (add-feature with PRD):** pipelineId=brownfield-add-feature with refined-prd + existing architecture → use `.nayan/guidance/architecture-impact-add-feature.md`; produce **architecture impact** (addendum to architecture.md or impact section), not a full new architecture; then hand off to prototype/plan. **When handed off from brainstorm** (e.g. after JIRA/SOW for extend or migrate): use the condensed scope or migration brief provided in the handoff message; context was already fetched and user-aligned in brainstorm — do not re-fetch JIRA/SOW unless the message asks for additional context.
2. **Verify prerequisites** — **Always check first** (whether entered via workflow or directly). **Greenfield:** refined-prd.md with **Sign-Off (Section 1) all three roles Approved, Approver Name, and Sign-Off Date filled for each** — if Pending, Needs Revision, or missing Name/Date, **reject** and redirect to prd or user to complete sign-off. **Brownfield A:** condensed scope (from orchestrator or from **brainstorm** handoff when JIRA/SOW was input), existing architecture.md, codebase. **Brownfield Migrate:** migration brief or condensed scope (from orchestrator or from **brainstorm** handoff when JIRA/SOW was input), existing (legacy) architecture or system context, codebase. **Brownfield B (add-feature with PRD):** refined-prd.md with Sign-Off Approved, existing architecture.md, codebase. If not passed: redirect to **prd** (greenfield/B when PRD missing) or ask user (brownfield) or **brainstorm** (when scope was expected from brainstorm handoff but missing) per sdlc_prerequisites rule. When entered directly with missing prereqs: use new_task to redirect per sdlc-prerequisites. **Prerequisite vs todo:** Prerequisite verification is a gate at mode entry—do it before creating or executing the todo list. Do NOT add prerequisite verification as a todo item. Sign-off for the artifact being produced (architecture or architecture impact) must be the last todo. Do not mark Approved or hand off (new_task) or call attempt_completion until user has given explicit sign-off.
3. Read input: **Greenfield:** refined-prd.md — use Domain Glossary (Section 15 Appendix) and Non-Functional Expectations (Section 11) for naming and design. **Brownfield A:** condensed scope, existing architecture.md, existing codebase — use Key Domain Terms (condensed scope Section 2) for naming; consider scope's functional requirements and integration points. **Brownfield A:** Analyze existing architecture and codebase folder structure; **align** architecture to existing when the request fits, or **propose changes** when the request requires modifications to solve it (see `.nayan/guidance/architecture-brownfield-structure.md`). **Brownfield Migrate:** migration brief or condensed scope, legacy architecture or system context, codebase — produce pre/post architecture, migration strategy (big-bang vs phased vs parallel run), data migration, cutover plan, dual-run, verification per `.nayan/guidance/brownfield-migration-use-cases.md`. **Brownfield B (add-feature with PRD):** refined-prd.md + existing architecture.md + codebase — produce architecture impact per `architecture-impact-add-feature.md` (how feature fits, modules/APIs touched, impacted integrations, flow diagrams for new flows); do not create full new architecture. **For large files:** Use search-first and targeted reading per `.nayan/guidance/file-reading-strategy.md` — search for relevant sections (e.g., Use Cases, folder structure, tech stack) then read only needed ranges with offset/limit.
4. **Use MCP when configured:** Jira, Confluence, Google Drive, etc. — fetch architecture docs, tech specs, integration contracts, migration plans, and stakeholder context. **Context inputs:** Per `.nayan/guidance/context-input-handling.md` — when SOW or Jira is referenced in the request, fetch full context before creating architecture. **When entered from brainstorm handoff** (e.g. after JIRA/SOW for extend/migrate): the handoff message already contains the user-aligned scope or migration brief from brainstorm; use that as the primary input. Fetch additional JIRA/SOW context only if the message explicitly references another ticket or doc. Use for architecture decisions and technical specs.
5. Ask clarifying questions: product family, existing services, deployment target, compliance. **For greenfield:** ask tech stack (Bootcamp vs Enterprise vs Custom; see `2_tech_stacks.md`). **For greenfield Custom stack:** also ask database choice (SQLite, PostgreSQL, etc.) and migration strategy (auto-migrate on startup vs. Alembic/manual migrations). **For Bootcamp/Enterprise:** database is predetermined (MongoDB/Oracle); migration strategy should still be documented in architecture.md. **For brownfield (A, B, Migrate):** use existing architecture/codebase stack—do not re-ask tech stack. **For Migrate:** target stack may be new; document legacy vs target and migration path.
6. **HITL (greenfield only):** Confirm tech stack choice (and database/migration when Custom) with user before documenting
7. Consult architect-planning skill (Company Technology Stack section) for technology recommendations (greenfield). **If any component calls an LLM** (chat, summarization, extraction, classification, agent/tool use, RAG, code-gen, etc.) — consult **ai-feature-design** skill and record Phase 1 decisions (task type, model, latency/cost budget, failure mode, privacy, snapshot pinning) in architecture.md.
8. **HITL:** Present architectural pattern (Modular Monolith vs Decoupled Fullstack) and key modules; wait for user confirmation before detailed design. **Brownfield B (add-feature with PRD):** Skip or shorten; present impact scope (modules touched, new flows) for confirmation.
9. **Design system architecture** that satisfies the Refined PRD (greenfield) or condensed scope (brownfield A) or **migration scope** (brownfield Migrate) or **architecture impact** for add-feature (brownfield B). **Brownfield Migrate:** Document pre/post architecture, migration strategy, data migration, cutover, dual-run, verification per `brownfield-migration-use-cases.md`. Define: system components, boundaries, interfaces, data models, integration points, technology choices. **Brownfield B:** Document impact per `architecture-impact-add-feature.md` (addendum to architecture.md or impact section): how feature fits, modules/APIs touched, impacted integrations, flow diagrams for new flows; do not recreate full architecture. **Explicitly distinguish greenfield vs brownfield constraints:** legacy integration, migration paths, coexistence strategies. Output must be **complete enough that UX design and development planning can proceed with confidence**.
10. Create architecture.md (greenfield, brownfield A, brownfield Migrate) or **architecture impact** addendum/section (brownfield B) per the appropriate structure: **Greenfield** → `architecture-greenfield-structure.md`; **Brownfield A** → `architecture-brownfield-structure.md`; **Brownfield Migrate** → `architecture-brownfield-structure.md` (include pre/post, migration strategy, data migration, cutover per brownfield-migration-use-cases.md); **Brownfield B** → `architecture-impact-add-feature.md` (impact only; append to existing architecture.md or produce impact doc). Include all required sections for the context. **When Decoupled Fullstack:** Include Repository Strategy (single vs multi-repo) and, when multi-repo, Repo dirs per [.nayan/guidance/decoupled-fullstack-repo-strategies.md](.nayan/guidance/decoupled-fullstack-repo-strategies.md). Ensure **all use cases (greenfield) or scope (brownfield A) or migration scope (brownfield Migrate) or PRD use cases (brownfield B)** are covered (see `3_architecture_validation.md`). **After each diagram added:** self-review the doc — validate Mermaid diagrams for syntax errors and fix any issues before proceeding.
11. **Self-review** — Run through `3_architecture_validation.md`. Self-review the doc: validate all Mermaid diagrams in architecture.md (or impact doc) for syntax errors and fix any issues. Fix use case/scope coverage gaps. Do not present to user or handoff with unresolved Mermaid errors.
12. **HITL:** Present full architecture (or architecture impact for brownfield B, or migration architecture for brownfield Migrate) to user; confirm "Does this fully address all requirements?"; wait for explicit sign-off before handoff. Do not mark Approved or hand off (new_task) or call attempt_completion until user has given explicit sign-off.
13. **Handoff:** When the solution involves **UI** (user-facing interfaces), hand off to **prototype**. When the solution is **API-only or backend-only** (no user-facing UI), hand off to **plan** (dev-plan phase) directly. Use `.nayan/rules-architect/4_handoff.xml`.

Include `TECH_STACK: bootcamp|enterprise|custom` in handoff so the next mode selects the correct skill.

See architect-planning skill. For LLM-backed features, see ai-feature-design skill. See sdlc_human_gates rule for Architecture sign-off gate.

**MCP:** When MCP servers (Jira, Confluence, Google Drive, etc.) are configured, use them proactively to gather architecture docs, tech specs, and dependency context. **Context inputs:** Per `.nayan/guidance/context-input-handling.md` — fetch SOW or Jira context before creating architecture.
