# Prototype Workflow

Create UX and UI concepts directly informed by the approved architecture and refined requirements. Produce wireframes, interaction flows, and visual design prototypes to validate the user experience. **Do not proceed to Plan (development plan) until UX and UI design have been validated and explicitly approved.**

## Before Any Work

0. **Expertise check (on every message):** Before responding to ANY message — including follow-ups and subsequent turns — check if the user or Nayan asks something outside this mode's expertise (per MODE RESTRICTION). If yes, hand off per `.nayan/guidance/expertise-handoff.md`. Do not attempt in-place or create a subtask. Do not skip on the next message.

## Prerequisites

- architecture.md (approved)
- refined-prd.md (greenfield) or condensed scope (brownfield)
- CONTEXT: greenfield | brownfield

## Workflow

1. **Verify prerequisites** — **Always check first** (whether entered via workflow or directly). architecture.md, refined-prd or condensed scope. **When refined-prd is input:** Verify Sign-Off (Section 1) has all roles Approved — **reject and redirect if Pending or Needs Revision.** If not passed: redirect to **architect** or **prd** per sdlc_prerequisites rule. When entered directly with missing prereqs: use new_task to redirect per sdlc-prerequisites.
2. **Read context** — architecture.md (components, data flows, UI-relevant modules), refined-prd (use cases Section 7, acceptance criteria, **Section 5 Users & Personas**) or condensed scope (functional scope, key domain terms, personas). **For large files:** Use search-first and targeted reading per `.nayan/guidance/file-reading-strategy.md` — search for Section 5, Section 7, use cases, personas, then read only needed ranges. **Brownfield:** When condensed scope has no explicit personas, infer from functional scope, feature description, or architecture (user types). When brownfield, scope or PRD may have originated from **brainstorm** (e.g. after JIRA/SOW) and been passed via architect or prd — use the scope or refined-prd from the handoff message.
   2a. **Design discovery (when UI involved)** — When PRD Section 12 or condensed scope lacks sufficient design direction, ask follow-up questions per `.nayan/guidance/prototype-design-discovery.md`. Cover: aesthetic preference; visual depth/surface style (flat, skeuomorphic, neumorphism, glassmorphism); theme (light/dark/system) and accessibility (high contrast, reduced motion); responsive strategy (breakpoints, mobile-first vs desktop-first); design system/component library (Material, Fluent, Tailwind, shadcn, Radix, Chakra, custom); material types (2D, 3D, animation, video, immersive as applicable); and per-type preferences. **Ask one question at a time.** **Skip** design discovery when Figma design, screenshots, or UI mockups are provided in PRD Section 12 or scope — the design is the source of truth; proceed to prototype creation with pixel-by-pixel matching per `.nayan/guidance/prototype-figma-matching.md`. **When brownfield and existing app has UI code:** Skip design discovery for aesthetic, theme, colors, typography, design system — existing UI is the source of truth; run step 2b and match existing UI pixel by pixel per `.nayan/guidance/prototype-brownfield-existing-ui.md`. Ask discovery only for net-new UI elements that have no existing pattern in the codebase. Skip or abbreviate when PRD/scope already specifies design assets, brand guidelines, and material types clearly.
   2b. **Brownfield: existing UI and prototype analysis (when existing app has UI code)** — **Before** creating new prototypes, **deeply understand existing UI**. (1) **Analyze existing UI code:** Inspect the codebase for UI layer — folder structure (e.g. components/, pages/, views/, styles/), component patterns (reusable vs page-specific), styling approach (CSS modules, Tailwind, design tokens, theme), layout and navigation, **design library in use** (Material, Fluent, Tailwind, shadcn, Radix, Chakra, etc.) and **custom components** (shared buttons, cards, modals, etc.). Document: key screens, flows, components, and visual patterns so the new prototype **adds to or enhances** existing UI rather than ignoring it. Extract **exact specs** from existing code: colors, spacing, typography, component structure, so the prototype can match **pixel by pixel**. **Production alignment:** When a design lib or custom components are used, the prototype must consider the **production solution based on that only** — prototype should reflect that same design lib and those custom component patterns so the development plan and code implement against the same stack. (2) **If an old prototype exists** (e.g. in `ux/prototypes/`, `prototypes/`, or paths from architecture/scope): **Analyze it** for enhancement opportunities — what screens and flows it covers, what to extend or refine, and how the requested add/enhancement fits. (3) **Then** generate prototype that **follows existing UI components, styles, and look-and-feel pixel by pixel**; reuse or replicate existing component structure and styling exactly (using the specs extracted in (1)); add or enhance only within that visual system unless scope explicitly requests a change. When the app uses a **design library or custom components**, the prototype must be **production-solution aligned**: use that same design lib (or replicate its patterns) and those custom component concepts so plan and code implement based on that only. For **migration** (brownfield-migrate), align new prototype to target architecture while matching legacy UI pixel-by-pixel where continuity is required.
3. **Create UX and UI concepts** — Wireframes, interaction flows, visual design prototypes. **Required:** Generate **one responsive HTML prototype per persona** (each persona from PRD Section 5 or condensed scope). Each prototype must exactly mimic that persona's views/pages (login + all pages that persona can access). Include **all screens** per persona (from use cases or functional scope — every step with UI). Use **in-page feedback** (toasts, modals) — no `alert()`. No placeholder content (TODO, TBD, placeholder images). Prototypes must be **fully functional**, **one web responsive to all devices** (single prototype per persona that adapts to mobile/tablet/desktop — not separate versions), and **integrated** — all screens wired together and navigable; no isolated screens. Include empty states, loading states, success/error/confirmation states. Save to `ux/prototypes/{persona}/` or `prototypes/{persona}/`. Ensure artifacts are informed by the approved architecture and requirements. See `.nayan/guidance/ux-artifacts.md` for persona-specific prototype requirements. **When Figma or design assets are provided:** Prototypes must **match the design pixel-by-pixel** (exact colors, spacing, typography, layout). Use Figma MCP or Locofy when available; otherwise extract specs per `.nayan/guidance/prototype-figma-matching.md`. **Brownfield (existing app with UI):** Prototype must be informed by step 2b — **add to or enhance existing UI features** while **following existing UI components, styles, and look-and-feel pixel by pixel** (exact colors, spacing, typography, component structure from the codebase). When the app uses a **design library or custom components**, consider the **production solution based on that only** — prototype must reflect that design lib and those custom components so the development plan and code implement using the same stack. If an old prototype exists, **enhance it** (extend screens, refine flows, add new features) rather than replacing from scratch where the existing prototype remains valid.
4. **Present for stakeholder review** — Artifacts must be in a form that stakeholders can review and approve. **Primary:** Interactive HTML prototype that users can open to see how the UI works. **Secondary:** Mermaid diagrams, markdown descriptions, links to Figma/Figma-like outputs, or embedded sketches.
5. **Open in browser for review** — Once prototypes are ready, **open each persona's prototype in the browser** so the user can review interactively. Run `open ux/prototypes/{persona}/index.html` (macOS) or `start ux/prototypes/{persona}/index.html` (Windows) or equivalent for each persona. If opening fails, provide the file path and instruct: "Open [path] in your browser to review."
   5a. **Self-verification (before HITL)** — Before asking "Do you approve this UX and UI design?", create a **granular todo list** and verify each item one by one against PRD (refined-prd) or condensed scope and architecture.md. **MANDATORY:** Use todo_write to create a todo for each verification point; verify one by one; mark complete only when verified. Do not proceed to HITL until all todos pass. If any gap is found, fix the prototype and re-run. See `.nayan/guidance/prototype-self-verification.md` for the granular todo structure.
6. **HITL:** Present UX and UI design to user. Ask: "Do you approve this UX and UI design?" **Wait for explicit approval** before handoff to plan.
7. **If UX findings require changes:**
    - Before returning to prd/architect or iterating: Ask clarifying questions per `.nayan/guidance/prototype-design-discovery.md`. "What would you like to change?" — offer options including layout, colors, typography, 2D/3D/animation style, interactions.
    - If the user **explicitly requests a UI change** (greenfield or brownfield): Consider **prototype (create/update) → plan (create/update) first**; use **architect (create/update)** only when there is API or architecture impact (new/changed APIs, backend, data model, new modules or integration points). Do not hand off to code until prototype and plan (and architect when applicable) are created or updated and approved. See `.nayan/guidance/pipeline-entry-points.md` (Explicit UI change requests).
    - If **requirements** need adjustment → indicate this; request return to **prd** (greenfield) or user (brownfield).
    - If **architecture** needs adjustment → indicate this; request return to **architect**.
    - Do NOT hand off to plan until requirements and architecture are updated and re-approved.
8. **When approved:** Hand off to **plan** with architecture, PRD/scope, and UX artifacts (wireframes, interaction flows, prototypes).

## Output

- **Interactive HTML prototype (per persona)** — One prototype per persona; each mimics that persona's exact views/pages
- Complete screen coverage (all use case steps with UI); in-page feedback only; no temp/todo/placeholder content; fully functional; one web responsive to all devices; integrated screens (all navigable from within prototype)
- Wireframes, interaction flows, visual design prototypes
- UX artifacts in a form stakeholders can review and approve
- **Brownfield (existing app with UI):** Prototype matches existing UI components, styles, and look-and-feel pixel by pixel; add/enhance only within that visual system

## Handoff

- **Approved:** plan (with architecture, PRD/scope, UX artifacts)
- **Requirements need change:** prd or user
- **Architecture need change:** architect

See `.nayan/guidance/ux-artifacts.md` for artifact formats and approval criteria. See `.nayan/guidance/prototype-self-verification.md` for the self-verification protocol and granular todo structure. **Brownfield existing UI:** See `.nayan/guidance/prototype-brownfield-existing-ui.md` for analyze-then-add/enhance flow.
